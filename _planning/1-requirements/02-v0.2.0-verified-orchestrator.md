# Requirements: v0.2.0 - High-Performance Verified Orchestrator

## Goal
Transform Klei from a simple conversation partner into a high-performance, formally verified LLM orchestrator capable of advanced reasoning, tool calling, and agent coordination with compile-time correctness guarantees.

## Motivation
Version 0.1.0 demonstrated the viability of a Lean-only approach for LLM interaction. However, to build a production-ready "personal agentic AI backend," we need:

1. **Advanced Reasoning**: Larger models (20B+ parameters) with tool-calling capabilities
2. **Performance**: Efficient memory management for long contexts (32k+ tokens) in constrained VRAM
3. **Security**: Isolated, permission-based communication without network exposure
4. **Correctness**: Formal verification of agent state transitions and tool invocations

## Target Environment

### Hardware Constraints
- **VRAM**: 16 GB total
  - Model: ~11-13 GB (Q4 quantized 20B model)
  - KV Cache: ~3-5 GB (supporting 32k+ context)
  - Overhead: ~1-2 GB

### Software Stack
- **OS**: Linux (WSL2 with GPU passthrough supported)
- **CUDA**: For GPU acceleration
- **Nix**: Reproducible development environment

## Functional Requirements

### 1. Advanced LLM Integration

**Model Selection:**
- Primary: **GPT-OSS 20B** (Q4 quantization) or **Qwen3 14B**
- Requirements:
  - Native tool-calling support
  - Strong reasoning capabilities
  - 32k+ context window
  - Efficient Q4 quantization available

**Inference Engine:**
- **vLLM** as replacement for Ollama
- Required features:
  - Native MCP (Model Context Protocol) support
  - PagedAttention for memory efficiency
  - Batch processing capabilities
  - OpenAI-compatible API
  - Unix Domain Socket support

### 2. Communication Layer Upgrade

**Unix Domain Sockets (UDS):**
- Replace HTTP/curl with UDS for Lean ↔ vLLM communication
- Benefits:
  - **Security**: POSIX filesystem permissions, no network exposure
  - **Performance**: Lower latency than TCP loopback
  - **Simplicity**: No port management, firewall rules, or TLS overhead

**Implementation Requirements:**
- Lean 4 FFI bindings for socket operations
- C shim for `AF_UNIX` socket handling
- Efficient binary protocol or JSON over socket
- Connection pooling/reuse

### 3. Formal Verification

**Type-Safe Tool Calls:**
- All tool invocations must be verified at compile time
- Invalid tool calls should be rejected by the type system
- Tool schemas represented as inductive types

**Verified State Machine:**
- Agent decision-making modeled as a formal state machine
- State transitions proven correct before execution
- Options for representation:
  - **Kleisli Category**: Compose effectful computations with verification
  - **Inductive State Machine**: Explicit states and transition rules

**JSON Schema Verification:**
- Parser that maps LLM JSON outputs to Lean types
- Compile-time guarantee of schema compliance
- Graceful handling of malformed responses

### 4. Agent Orchestration

**Tool System:**
- Extensible tool registry
- Type-safe tool definitions
- Parameter validation via dependent types
- Error handling with verified recovery strategies

**Context Management:**
- Efficient KV cache utilization
- Long-context window support (32k+ tokens)
- Conversation history pruning strategies
- Memory-aware context windowing

**Multi-Turn Conversations:**
- Stateful conversation management
- Context preservation across turns
- Tool result integration into context

## Non-Functional Requirements

### Performance
- **Latency**: First token < 500ms (warm cache)
- **Throughput**: Handle long contexts (32k tokens) efficiently
- **Memory**: Stay within 16 GB VRAM budget
- **CPU**: Minimal CPU overhead for orchestration

### Security
- **Isolation**: UDS prevents network-based attacks
- **Permissions**: Filesystem ACLs control access
- **Validation**: All inputs verified against formal schemas
- **Sandboxing**: Tool execution in isolated contexts (future)

### Reliability
- **Error Handling**: Graceful degradation on LLM failures
- **Recovery**: Automatic retry with exponential backoff
- **Logging**: Structured logs for debugging
- **Monitoring**: VRAM usage tracking

### Maintainability
- **Modularity**: Clear separation of concerns
- **Documentation**: Inline proofs and documentation
- **Testing**: Property-based tests for verified components
- **Versioning**: Stable API boundaries

## Out of Scope for v0.2.0

These features are deferred to future versions:

- Multi-model orchestration (different models for different tasks)
- Distributed agent coordination across machines
- Web UI or API gateway
- Persistent storage and retrieval (RAG)
- Fine-tuning or model customization
- Multi-user support

## Success Criteria

Version 0.2.0 is complete when:

1. ✓ vLLM runs a 20B Q4 model within 16 GB VRAM
2. ✓ Lean core communicates with vLLM via Unix Domain Sockets
3. ✓ Tool calls are type-safe and formally verified
4. ✓ Agent state machine is proven correct
5. ✓ JSON parser maps LLM outputs to verified Lean types
6. ✓ System handles 32k+ token contexts efficiently
7. ✓ End-to-end latency meets performance targets
8. ✓ Documentation covers architecture and verification proofs

## Migration Path from v0.1.0

1. Keep existing Ollama/curl code as fallback
2. Implement UDS communication layer alongside HTTP
3. Add vLLM support as alternative backend
4. Gradually migrate tool calls to verified types
5. Switch default backend to vLLM once stable
6. Remove Ollama dependency in future version
