# Requirements: v0.2.0 - vLLM Communication Channel

## Goal
Replace the HTTP/curl-based communication with a high-performance Unix Domain Socket (UDS) layer and migrate from Ollama to vLLM for improved inference capabilities.

## Motivation
Version 0.1.0 demonstrated the viability of a Lean-only approach for LLM interaction. However, the current HTTP/curl implementation has limitations:

1. **Performance Overhead**: curl subprocess spawning adds ~100-200μs latency per request
2. **Limited Scalability**: Can't support larger models or longer contexts efficiently
3. **Network Exposure**: HTTP requires port management even on localhost
4. **Suboptimal Inference**: Ollama lacks advanced features like PagedAttention and efficient KV cache management

Version 0.2.0 addresses these by:
- Implementing direct UDS communication (< 50μs latency)
- Migrating to vLLM for better memory efficiency and larger model support
- Removing network stack overhead and security concerns

## Target Environment

### Hardware Constraints
- **VRAM**: 16 GB total
  - Model: ~11-13 GB (Q4 quantized 20B model)
  - KV Cache: ~3-5 GB (supporting 32k+ context)
  - Overhead: ~1-2 GB

### Software Stack
- **OS**: Linux (WSL2 with GPU passthrough supported)
- **CUDA**: For GPU acceleration
- **Nix**: Reproducible development environment
- **vLLM**: Latest stable version with UDS support

## Functional Requirements

### 1. vLLM Integration

**Inference Engine:**
- Replace Ollama with **vLLM**
- Features utilized:
  - PagedAttention for memory efficiency
  - OpenAI-compatible API
  - 32k+ context window support
  - Q4 quantization (AWQ or GPTQ)
  - Unix Domain Socket listener

**Model Support:**
- Primary target: **20B parameter models** (e.g., GPT-OSS 20B, Qwen2.5 14B)
- Must fit in 16 GB VRAM with Q4 quantization
- Support for 32k context window minimum

**Configuration:**
- Serve via Unix Domain Socket at `/tmp/vllm.sock`
- Socket permissions: 0600 (owner-only)
- VRAM utilization: 90% maximum
- Enable prefix caching for system prompts
- KV cache dtype: auto (FP8 if available)

### 2. Unix Domain Socket Communication Layer

**C FFI Implementation:**
- C shim library (`libklei_socket.so`) wrapping POSIX socket API
- Functions required:
  - `klei_socket_connect(path)`: Connect to UDS
  - `klei_socket_send(sock, data, len)`: Send bytes
  - `klei_socket_recv(sock, buffer, size, timeout)`: Receive bytes
  - `klei_socket_close(sock)`: Close connection
  - `klei_socket_error(sock)`: Get error message

**Lean FFI Bindings:**
- Type-safe wrappers around C functions
- Integration with Lean's IO monad
- Proper resource management (connection lifecycle)
- Error handling with Except monad

**Protocol Layer:**
- JSON-RPC 2.0 over UDS
- Newline-delimited JSON messages
- Request/response correlation via ID
- Support for streaming responses (future)

### 3. Lean Core Integration

**vLLM Client Module:**
- New module: `Klei.vLLM` (alongside existing `Klei.Ollama`)
- API functions:
  - `generate`: Send prompt, receive completion
  - `chat`: Multi-turn conversation (system + messages)
  - Compatibility with existing REPL interface

**Backwards Compatibility:**
- Keep `Klei.Ollama` module functional
- Environment variable `KLEI_BACKEND` to switch backends:
  - `ollama` (default for v0.2.0 development)
  - `vllm` (to be tested and switched to default)
- REPL should work identically regardless of backend

**Error Handling:**
- Graceful degradation if vLLM is not running
- Connection retry with exponential backoff
- Timeout handling (configurable, default 30s)
- User-friendly error messages

### 4. Development Environment

**Nix Integration:**
- Add vLLM to `flake.nix` build inputs
- Helper function `start-vllm`:
  - Start vLLM server with UDS configuration
  - Pull model if not available
  - Set up socket permissions
  - Monitor server health

**Model Management:**
- Models stored in `.vllm/models` (similar to `.ollama/models`)
- Environment variable `VLLM_MODELS` for model path
- Initial model: Start with smaller model for testing (e.g., Qwen2.5 7B)
- Production model: 20B parameter model after validation

## Non-Functional Requirements

### Performance
- **UDS Latency**: < 50μs round-trip (socket only, excluding inference)
- **First Token Latency**:
  - Cold (no cache): < 2s
  - Warm (cached prefix): < 500ms
- **Throughput**: Handle 32k context efficiently
- **Memory**: Stay within 16 GB VRAM budget

### Security
- **Isolation**: Socket file with 0600 permissions (owner-only)
- **No Network**: No TCP ports exposed
- **Validation**: Basic input validation before sending to vLLM
- **Logging**: Log all requests for debugging (opt-in)

### Reliability
- **Connection Management**: Persistent connection with automatic reconnect
- **Error Recovery**: Retry on transient failures (max 3 attempts)
- **Graceful Degradation**: Fall back to Ollama if vLLM unavailable
- **Resource Cleanup**: Proper socket closure on exit

### Maintainability
- **Modularity**: Clear separation between UDS layer and vLLM client
- **Documentation**: Inline comments for C shim and FFI
- **Testing**: Unit tests for socket operations
- **Compatibility**: Maintain existing REPL interface

## Out of Scope for v0.2.0

The following features are explicitly deferred to future versions:

- **Tool Calling** (v0.3.0): No tool execution or MCP integration
- **Formal Verification** (v0.3.0+): No state machine proofs or dependent types
- **Streaming Responses** (future): Only complete responses for now
- **Multiple Models**: Single model per vLLM instance
- **Conversation Persistence**: No database or file-based history
- **Web UI**: CLI only

## Success Criteria

Version 0.2.0 is complete when:

1. ✓ C shim compiles and links with Lean executable
2. ✓ Lean FFI bindings successfully call C socket functions
3. ✓ Connection established to vLLM via UDS
4. ✓ JSON-RPC messages sent and received correctly
5. ✓ vLLM generates completions for prompts
6. ✓ REPL works with vLLM backend (same UX as v0.1.0)
7. ✓ Performance targets met (< 50μs UDS latency)
8. ✓ 20B model runs within 16 GB VRAM
9. ✓ Nix environment includes vLLM with `start-vllm` helper
10. ✓ Documentation updated with new backend usage

## Migration Path from v0.1.0

### Phase 1: Parallel Implementation
- Implement UDS layer alongside HTTP/curl
- Add vLLM client without removing Ollama
- Feature flag to switch backends
- Test with smaller models first

### Phase 2: Integration Testing
- End-to-end testing with vLLM
- Performance benchmarking (latency, throughput, VRAM)
- Compare output quality between Ollama and vLLM
- Load testing with long contexts

### Phase 3: Default Switch
- Change default backend to vLLM
- Update documentation and README
- Keep Ollama as fallback option
- Tag as v0.2.0 release

### Phase 4: Cleanup (v0.3.0+)
- Remove Ollama code (optional)
- Remove HTTP/curl dependency
- Deprecate old configuration options

## Dependencies

### External
- vLLM (>= 0.6.0) with UDS support
- CUDA-compatible GPU with 16 GB VRAM
- POSIX-compliant OS (Linux, WSL2)
- C compiler (gcc or clang)

### Internal
- Lean 4 (>= 4.25.0)
- Lake build system
- Existing Klei core modules
