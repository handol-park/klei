# Implementation Plan: v0.2.0 - vLLM Communication Channel

## Overview

This document provides a step-by-step implementation plan for v0.2.0, which focuses exclusively on replacing the HTTP/curl communication layer with Unix Domain Sockets and migrating from Ollama to vLLM.

**Timeline Approach:** This plan breaks work into milestones without time estimates. Complete each milestone before moving to the next.

## Project Structure

```
core/
├── FFI/
│   ├── socket.h           # C header (NEW)
│   ├── socket.c           # C implementation (NEW)
│   └── Makefile           # Build C shim (NEW)
├── Klei/
│   ├── Communication/
│   │   ├── Socket.lean    # Lean FFI bindings (NEW)
│   │   └── Protocol.lean  # JSON-RPC layer (NEW)
│   ├── vLLM.lean          # vLLM client (NEW)
│   ├── Ollama.lean        # Keep for backwards compat
│   └── Backend.lean       # Backend abstraction (NEW)
├── Main.lean              # Update to support both backends
└── lakefile.toml          # Update build config
```

## Milestones

### Milestone 1: C Socket Layer

**Goal:** Implement and test C shim for UDS operations

#### Tasks

1. **Create FFI directory structure**
   ```bash
   mkdir -p core/FFI
   ```

2. **Write socket.h header**
   - Define opaque `klei_socket_t` handle type
   - Declare connection, send, recv, close, error functions
   - Document error codes enum
   - Location: `core/FFI/socket.h`

3. **Implement socket.c**
   - `klei_socket_connect`: Connect to UDS path
   - `klei_socket_send`: Write bytes to socket
   - `klei_socket_recv`: Read bytes with timeout
   - `klei_socket_close`: Clean up resources
   - `klei_socket_error`: Return last error message
   - Location: `core/FFI/socket.c`
   - See specification: `_planning/3-specification/02-uds-communication.md`

4. **Create Makefile**
   - Compile shared library: `libklei_socket.so`
   - Flags: `-shared -fPIC -Wall -Wextra`
   - Test target: compile and run basic test
   - Location: `core/FFI/Makefile`

5. **Write C test program**
   - Create `core/FFI/test_socket.c`
   - Test connect, send, recv, close
   - Requires mock UDS server (use `nc -U` or Python script)
   - Validate error handling

6. **Build and test**
   ```bash
   cd core/FFI
   make
   ./test_socket
   ```

**Acceptance Criteria:**
- C shim compiles without warnings
- Test program connects to mock UDS server
- Send/recv works correctly
- Error handling returns meaningful messages
- No memory leaks (verify with valgrind if available)

### Milestone 2: Lean FFI Bindings

**Goal:** Create type-safe Lean interface to C socket layer

#### Tasks

1. **Create Communication module**
   ```bash
   mkdir -p core/Klei/Communication
   ```

2. **Write Socket.lean**
   - Define `SocketHandle` opaque type
   - Define `SocketError` inductive type
   - Declare `@[extern]` functions for C FFI
   - Implement high-level wrappers:
     - `connect : String → IO (Except SocketError SocketHandle)`
     - `send : SocketHandle → ByteArray → IO (Except SocketError Unit)`
     - `recv : SocketHandle → Nat → Nat → IO (Except SocketError ByteArray)`
     - `close : SocketHandle → IO Unit`
   - Implement `withSocket` resource manager
   - Location: `core/Klei/Communication/Socket.lean`

3. **Update lakefile.toml**
   - Add linkage flags for `libklei_socket.so`
   - Add pre-build step to compile C shim
   - Example:
     ```toml
     [[lean_exe]]
     name = "core"
     root = "Main"
     moreLinkArgs = ["-L./FFI", "-lklei_socket"]
     ```

4. **Write Lean socket test**
   - Create `core/Test/Socket.lean` (or inline in Socket.lean)
   - Test connection to mock server
   - Test send/recv with known data
   - Test error cases (invalid path, timeout)

5. **Build and test**
   ```bash
   cd core
   lake build
   # Run Lean test (if executable)
   ```

**Acceptance Criteria:**
- Lean code compiles and links with C shim
- FFI calls succeed without crashes
- Errors are properly converted to Lean `Except` types
- Resource cleanup happens (socket closes)

### Milestone 3: JSON-RPC Protocol Layer

**Goal:** Implement JSON-RPC 2.0 over UDS

#### Tasks

1. **Write Protocol.lean**
   - Define `Request` structure (jsonrpc, method, params, id)
   - Define `Response` structure (jsonrpc, result, error, id)
   - Derive `ToJson` and `FromJson` instances
   - Implement `call` function:
     - Serialize request to JSON
     - Send via socket
     - Receive response
     - Parse and validate JSON
   - Define `ProtocolError` type
   - Location: `core/Klei/Communication/Protocol.lean`

2. **Implement newline-delimited JSON**
   - Append `\n` to each message
   - Handle streaming reads (accumulate until `\n`)
   - Parse complete messages

3. **Add helper functions**
   - `generateId`: Unique request IDs (use counter or timestamp)
   - `validateResponse`: Check jsonrpc version, ID match
   - `extractResult`: Get result field or error

4. **Write protocol tests**
   - Mock JSON-RPC server (Python script or Lean mock)
   - Test request serialization
   - Test response parsing
   - Test error handling

**Acceptance Criteria:**
- JSON-RPC requests serialize correctly
- Responses parse correctly
- Error responses handled gracefully
- ID correlation works

### Milestone 4: vLLM Client Implementation

**Goal:** Create vLLM client using UDS protocol

#### Tasks

1. **Write vLLM.lean**
   - Define `GenerateParams` structure:
     - `prompt : String`
     - `max_tokens : Nat`
     - `temperature : Float`
     - `stream : Bool := false`
   - Implement `generate` function:
     - Construct JSON-RPC request for `/v1/completions`
     - Call protocol layer
     - Extract text from response
   - Implement `chat` function (optional, for multi-turn):
     - Use `/v1/chat/completions` endpoint
     - Support messages array
   - Location: `core/Klei/vLLM.lean`

2. **Define vLLM API types**
   - Match OpenAI-compatible API format
   - `CompletionRequest`, `CompletionResponse`
   - `ChatRequest`, `ChatMessage`, `ChatResponse`
   - Derive JSON instances

3. **Add configuration**
   - Socket path from environment: `VLLM_SOCKET` (default: `/tmp/vllm.sock`)
   - Timeout from environment: `VLLM_TIMEOUT` (default: 30000ms)
   - Model name parameter (default: read from vLLM server)

4. **Error handling**
   - Connection failures → retry with backoff
   - Timeout errors → return clear message to user
   - Invalid responses → log and return error

**Acceptance Criteria:**
- vLLM client sends valid OpenAI API requests
- Responses parsed correctly
- Text extraction works
- Configuration via environment variables

### Milestone 5: Backend Abstraction

**Goal:** Create unified interface for Ollama and vLLM

#### Tasks

1. **Write Backend.lean**
   - Define `Backend` inductive type:
     ```lean
     inductive Backend where
       | ollama
       | vllm
     ```
   - Define `BackendAPI` structure class:
     ```lean
     structure BackendAPI where
       generate : String → IO (Except Error String)
       configure : IO Unit
     ```
   - Implement instances for Ollama and vLLM
   - Location: `core/Klei/Backend.lean`

2. **Add backend selection**
   - Read `KLEI_BACKEND` environment variable
   - Parse to `Backend` type
   - Default: `ollama` (for compatibility)
   - Function: `selectBackend : IO Backend`

3. **Unified API**
   - Single `generate` function that dispatches to backend
   - Hide implementation details from caller
   - Consistent error types

**Acceptance Criteria:**
- Both backends work through unified API
- Environment variable switching works
- Same REPL experience regardless of backend

### Milestone 7: vLLM Environment Setup

**Goal:** Integrate vLLM into Nix development environment

#### Tasks

1. **Update flake.nix**
   - Add `vllm` to build inputs (may need to package for Nix)
   - Alternative: Use Python with pip/uv to install vLLM
   - Add vLLM models directory: `export VLLM_MODELS="$PWD/.vllm/models"`
   - Set socket path: `export VLLM_SOCKET="/tmp/vllm.sock"`

2. **Create start-vllm helper**
   - Similar to `start-ollama`
   - Start vLLM server:
     ```bash
     vllm serve MODEL_NAME \
       --uvicorn-unix-socket /tmp/vllm.sock \
       --uvicorn-unix-socket-perms 0600 \
       --quantization awq \
       --dtype half \
       --max-model-len 32768 \
       --gpu-memory-utilization 0.90 \
       --enable-prefix-caching
     ```
   - Check if server is running (ping socket)
   - Download model if not present
   - Set restrictive socket permissions

3. **Model selection**
   - Start with smaller model for testing: `Qwen/Qwen2.5-7B-Instruct-AWQ`
   - Production model: `HuggingFaceH4/gpt-oss-20b-AWQ` or similar
   - Allow model override via environment: `VLLM_MODEL`

4. **Document setup**
   - Update README.md with vLLM setup instructions
   - Document model requirements
   - Add troubleshooting section

**Acceptance Criteria:**
- vLLM available in Nix shell
- `start-vllm` command works
- Socket created with correct permissions
- Model downloads and loads
- Server responds to requests

## Risk Mitigation

### Risk 1: C FFI Integration Complexity
- **Mitigation:** Start with simplest possible C code, test thoroughly
- **Fallback:** Use existing curl/HTTP as temporary solution

### Risk 2: vLLM Availability in Nix
- **Mitigation:** Use Python/pip within Nix shell if needed
- **Fallback:** Manual vLLM installation with documentation

### Risk 3: Performance Not Meeting Targets
- **Mitigation:** Profile early, optimize hot paths
- **Fallback:** Adjust targets based on real-world measurements

### Risk 4: 16 GB VRAM Budget Exceeded
- **Mitigation:** Test with smaller models first, use quantization
- **Fallback:** Support 14B models instead of 20B

### Risk 5: Breaking Changes in vLLM API
- **Mitigation:** Pin specific vLLM version
- **Fallback:** Abstract API changes in protocol layer

## Success Metrics

At the end of v0.2.0, we should achieve:

- ✓ UDS latency < 50μs (measured with benchmark)
- ✓ vLLM serving 20B model in < 16 GB VRAM
- ✓ First token latency < 500ms (warm cache)
- ✓ 32k context window supported
- ✓ REPL works identically to v0.1.0 (from user perspective)
- ✓ Both Ollama and vLLM backends functional
- ✓ Zero regressions from v0.1.0
- ✓ Complete documentation and examples

The communication layer built in v0.2.0 will be the foundation for all future features.
